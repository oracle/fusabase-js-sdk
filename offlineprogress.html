OracleDB Offline Support By Example

This page explains the offline architecture using concrete SDK calls. The detailed requirements are in offlineprogress.md.

The Components In Plain Terms

Think of the offline system as four cooperating parts:

Public API addDoc, setDoc, getDocs, onSnapshot. These parse user input and create internal mutations or queries.
OfflineSyncCoordinator The traffic controller. It decides what goes to local cache, what goes to ORDS, and when listeners/promises are resolved.
OfflineLocalStore IndexedDB-backed local state: cached docs, queued writes, optimistic overlays, active query metadata.
OfflineRemoteStore Network side: sends writes, replays queued batches, listens over WebSocket/long polling, handles retries and backend errors.

Example 1: User Adds A City While Offline

offline-safe addDoc

The user is offline and adds a city with a known ID. This can internally behave like setDoc(doc(collectionRef, id), data), but with create-only semantics.

await addDoc(collection(db, "cities"), "SF", {
  name: "San Francisco",
  population: 873965
});
Application
Calls the API

The app calls addDoc(collection(db, "cities"), "SF", data). The ID is known before any backend call.

Public API
Creates a mutation

The SDK creates a document path cities/SF and a create-only set mutation with precondition exists(false).

OfflineSyncCoordinator
Starts a local write

The write is handed to OfflineSyncCoordinator.write(). The returned promise stays pending until ORDS confirms or rejects the write.

OfflineLocalStore
Queues and applies locally

The mutation is stored in IndexedDB's mutation queue. An optimistic overlay makes cities/SF visible in local reads and listeners.

Application
Immediately sees pending data

Listeners fire with the new city. Snapshot metadata says hasPendingWrites=true.

OfflineRemoteStore
Waits for network

Because the device is offline, the write remains queued. No ORDS request is sent yet.

Later: ORDS accepts

SDK stores returned version, clears the overlay, emits hasPendingWrites=false, and resolves the promise.

Later: ORDS rejects

SDK rolls back cities/SF, emits a removal/revert event, and rejects the promise.

Still offline

The city remains visible as pending. The mutation stays in IndexedDB.

Example 2: User Increments A Counter Offline

field transforms 
await updateDoc(doc(db, "cities", "SF"), {
  visits: increment(1),
  updatedAt: serverTimestamp()
});
Public API
Separates normal fields from transforms

The SDK stores increment(1) and serverTimestamp() as field transforms, not plain values.

OfflineLocalStore
Applies local estimates

visits is incremented from the cached value. updatedAt stores local write time plus previous value.

Application
Controls timestamp display

The app can read pending timestamps as estimate, previous, or none.

docSnap.data({ serverTimestamps: "estimate" });
docSnap.data({ serverTimestamps: "previous" });
docSnap.data({ serverTimestamps: "none" });
ORDS
Returns authoritative transform results

On acknowledgement, ORDS returns final values in transformResults. The SDK replaces local estimates.

Example 3: User Reads Cities While Offline

cache vs server 
const snap = await getDocs(collection(db, "cities"));
OfflineSyncCoordinator
Checks network and source

Default getDocs() uses server when online. If offline, it falls back to cache.

OfflineLocalStore
Returns cached results

The SDK returns whatever matching docs it has locally. The result may be incomplete.

Application
Reads metadata

The snapshot has fromCache=true. That tells the app the result may be stale or partial.

Exact server read

Use getDocsFromServer(query). It rejects while offline.

Explicit local read

Use getDocsFromCache(query). It never contacts ORDS.

Default read

Use getDocs(query). Online: server. Offline: cache.

Example 4: Listener Sees Pending Then Confirmed Data

onSnapshot 
onSnapshot(collection(db, "cities"), { includeMetadataChanges: true }, snap => {
  render(snap.docs, {
    fromCache: snap.metadata.fromCache,
    hasPendingWrites: snap.metadata.hasPendingWrites
  });
});
OfflineLocalStore
Initial local view

The listener first receives the current cache view, including pending overlays.

OfflineRemoteStore
Remote listen when online

The SDK uses WebSocket or long polling. If reconnecting without resume tokens, it refetches the query.

ORDS
Sends server state

Server documents include versions. The SDK updates the cache and emits another snapshot.

Application
UI can show state changes

A row can show "Saving..." while hasPendingWrites=true, then become normal after acknowledgement.

Example 5: Batch Write While Offline

ORDS transaction flow 
const batch = writeBatch(db);
batch.set(doc(db, "cities", "SF"), { name: "San Francisco" });
batch.update(doc(db, "stats", "cities"), { count: increment(1) });
await batch.commit();
OfflineLocalStore
Stores one local OfflineWriteBatch

Both writes are one atomic local batch. Listeners see both optimistic changes together.

OfflineRemoteStore
Replays when online

The SDK creates an ORDS transaction ID, then sends each operation as the same normal write call shape with that transaction ID.

ORDS
Returns provisional versions per operation

Each operation returns documentId and version, but those versions are not applied as committed yet.

ORDS
Commit decides durability

Only after final transaction commit succeeds does the SDK apply collected versions and clear pending writes. If anything fails permanently, abort and rollback the whole local batch.

Backend Requirements From These Examples

  • Single writes return documentId and version; ideally also updateTime, commitTime, and transformResults.
  • Create-only precondition is needed for offline-safe addDoc(collectionRef, id, data).
  • Update precondition is needed for updateDoc against missing docs.
  • Permanent errors must be machine-readable so the SDK can rollback.
  • Retryable errors must be distinguishable so the SDK keeps mutations queued.
  • Batch writes keep current ORDS transaction behavior: operation calls return provisional versions, final commit confirms durability.
  • Query results should include document versions for cache reconciliation.
